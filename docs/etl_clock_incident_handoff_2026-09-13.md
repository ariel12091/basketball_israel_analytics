# ETL and clock-minute incident handoff (2026-09-13)

## What happened

- The GitHub Actions ETL schedule in `.github/workflows/etl-full.yml` was commented out, and the local Windows scheduled task was absent. The production database had not received the expected recent games.
- Nightly GitHub scheduling was restored at `15 21 * * *` UTC in commit `b6effdc`. This is 00:15 in Israel daylight time and 23:15 in standard time.
- The first hosted retry loaded game 397 but failed games 398 and 399 with duplicate stint keys. The provider clock can reset or move backward; `compute_stints` had used clock ordering and collapsed regulation quarters into one bucket. Stint generation now follows `(quarter, id)` and keeps quarters separate. This was committed and pushed as `b98ccb8` (`etl/etl_onoff.R`, `etl/etl_full.R`). GitHub Actions run [34657162244](https://github.com/ariel12091/basketball_israel_analytics/actions/runs/34657162244) completed successfully on that commit.
- That retry exposed a separate canonical-minute bug: game 398 showed 47.983 minutes and game 399 showed 46.800 minutes for each team. Their provider clocks jumped backward by up to 480 and 591 seconds respectively. The old segment formula clipped a negative interval to zero, then counted the replayed clock interval again as the clock caught up. Team Ratings' possession-based rating path did not depend on these segment minutes.

## Correction made in production

- `refresh_segment_clock_fields_for_games(int4[])` now computes a running maximum of raw event elapsed time, ordered by action ID per game/team. Segment starts and ends use that monotonic timeline. Raw event elapsed time and clock-regression audit values are retained.
- The production function was replaced through the direct DDL connection (port 5432). Games 398 and 399 were then updated separately in validated transactions. Verified canonical totals: game 398 = **39.98333** minutes for both teams; game 399 = **39.90000** minutes for both teams. The function touched 1,041 and 1,116 event rows respectively. Raw regression fields remained populated.
- The dependent refresh runner `tmp_refresh_monotonic_dependents.R` was run by the user. It reached its final, read-only player verification query, where it failed because that query initially referenced a nonexistent `minutes` column in `player_traditional_by_game`. That final query was corrected to use `seconds_on_floor / 60`; reaching it indicates the earlier refresh statements completed, but their individual output was not captured in this handoff. The script refreshes lineup totals, lineup four factors, player four factors, team metrics, player traditional, default clutch totals, on/off default, player advanced, player traditional MV, rolling team metrics, team four factors, and sub-lineup stats. Re-running those refreshes is unnecessary solely because of the verification-query error.
- The app continued to show old data because season-level results are cached under the `app_meta.etl_full_last_success` value. A manual database refresh does not bump that key. On 2026-09-12 the key was changed from `2026-09-11 23:20:46` to `2026-09-12 07:24:43` (Israel local-time formatted value), using `tmp_bump_app_data_version.R`. Existing Shiny sessions poll it about every 60 seconds. A fresh app-session display after the bump was **not** independently verified in this chat.
